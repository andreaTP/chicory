## Pattern-Based Reproducers (Not Reproducing Yet)

These attempt to reproduce the bug using the exact pattern but outside WASM execution context:

1. **UnsignedComparisonReproducer** - ASM-generated bytecode with pattern `Integer.compare(a + MIN_VALUE, b + MIN_VALUE) >= 0`
2. **DirectPatternReproducer** - Direct pattern `Integer.compareUnsigned(a, b) >= 0 ? TRUE : FALSE`
3. **OpcodeImplReproducer** - Uses `OpcodeImpl.I32_GE_U` directly
4. **FinalReproducer** - Multiple strategies with inlining prevention

## Key Insight

The bug **requires WASM execution context**. The pattern `Integer.compareUnsigned(a, b) >= 0` appears during actual WASM execution when memory bounds are checked. Simply calling the pattern in a Java loop doesn't trigger it - it needs to appear in the compiled WASM execution code.

## Pattern That Triggers Bug

From `OpcodeImpl.I32_GE_U`:
```java
return Integer.compareUnsigned(a, b) >= 0 ? TRUE : FALSE;
```

This creates the C2 IR pattern:
```
cmp (add a min_jint) (add b min_jint) >= 0
```

Which triggers the buggy `BoolNode::Ideal` optimization on buggy JDKs.
